## 0. Общие договорённости

- **Входа с паролем нет** (подтвердил бэкенд). На главной две кнопки; клиент выбирает персонажа из `GET /demo/users`, фронт кладёт его `id`
  (UUID, например `00000000-0000-0000-0000-000000000101` у Кофейни) в заголовок `X-Demo-User` каждого запроса. Учётки с паролями из `synthetic-data.md` в MVP не используются.
- **Расчёты делает бэкенд.** Вилка, зона (`APPROVE` / `UNDERWRITER` / `REJECT`), пороги `thresholds`, цена пятна,
  ежемесячный платёж и график — всё приходит в ответах. Фронт только показывает и отправляет действия.
- **Кнопки определяет `application.availableActions`** (`EDIT`, `EVALUATE`, `CLOSE_SPOT`, `SUBMIT`, `ACCEPT`, `SIGN`,
  `CANCEL`, `REVIEW_SPOT`, `ADD_SPOT`, `DECIDE`). Если действия нет в списке, кнопка скрыта или неактивна.
- **Деньги** — в копейках в API, в рублях на экране. **Ставки** — проценты годовых (`19.5` → «19,5%»).
- **Ошибки** — формат Problem (`VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `INVALID_TRANSITION`,
  `SOURCE_UNAVAILABLE`). `503 SOURCE_UNAVAILABLE`: источник или скоринг недоступен, заявка остаётся как была,
  экран показывает «Источник данных временно недоступен. Попробуйте позже.»
- **Статусы** — один словарь «код → подпись и цвет» в `src/statuses.ts`. Цвета бейджей выбрал фронт ⚠️ от себя.
- **Данные экранов** приходят через слой `src/api` (`VITE_USE_MOCKS`: моки или настоящий бэкенд).
- Адаптив: десктоп и мобильный (ширина карточки до 720 px).
- Тема Core Components: по ответу бэкенда берём `default`, если Лид не против. Границы шкалы вилки — открытый вопрос, см. раздел 6.

`application.status` и показывает нужный блок ⚠️ от себя (так экранов меньше и переходы не расходятся с бэком).

| Статус | Подпись | Экран / блок клиента | Экран андеррайтера |

### 2.3. Новая заявка — `/client/new` (T35)
| | |
|---|---|
| Получает | `GET /me` (компания, только чтение) и `GET /products`: `code`, `name`, `minAmount`, `maxAmount`, `allowedTerms` |
| Блок «Компания» | только чтение: название, ИНН, форма, адрес, руководитель, дата регистрации (поля без значения не показываются) |
| Поля формы | продукт (карточки), сумма (`SliderInput`, шаг 50 000 ₽ ⚠️ от себя, точное число можно ввести руками), срок (из `allowedTerms`), цель (текст до 1000 знаков), согласия |
| Согласия | `bki` (запрос в БКИ) и `personalData` (обработка данных) — оба обязательны для расчёта |
| Проверки на фронте | сумма и срок в пределах продукта; цель не пустая; оба согласия отмечены |
| Отправляет | `POST /applications` {`productCode`, `amount`, `termMonths`, `goal`, `consents`}, затем `POST /applications/{id}/evaluate` (кнопка «Рассчитать») → 2.3а |
| Ошибки | `503` — «Источник данных временно недоступен»; `400` — подсветка полей |

**Решено (бэкенд):** ИНН не вводится; компания берётся из выбранного пользователя, поэтому в `POST /applications` ИНН нет. На форме показываем данные компании только для чтения с подписью «Компания из вашего профиля в банке. После «Рассчитать» банк заново проверит её в ЕГРЮЛ, ФНС и БКИ».

### 2.3а. Проверяем данные компании — `/client/check?id=…`
| | |
|---|---|
| Получает | `GET /applications/{id}/checks`: `checkedAt`, `items[]` — `source` (`EGRUL`, `FNS`, `BKI`), `status` (`OK` / `WARNING` / `BLOCKED`), `facts[]`, `problems[]` |
| Показывает | источники по очереди: сначала спиннер «Запрашиваем источник…», затем галочка, восклицательный знак или крестик, что подтвердилось, красным — проблемы. Внизу итог и «Проверено <дата> в <время>» |
| Итог | есть `BLOCKED` — «заявка не может быть одобрена»; есть `WARNING` — «есть что устранить»; иначе «данные подтверждены» |

| Повторно | со страницы заявки в `COLLECTING` — ссылка «Что банк проверил о компании» |

**Статус:** сделано на моках.

### 2.4. Вилка и пятна — `COLLECTING` (T37, T36)
Главный экран: шапка, вилка, плашка зоны, список пятен, кнопки.

**Получает** `GET /applications/{id}`:

| Блок | Поля |
|---|---|
| Шапка | `product.name`, `company.name`, `amount`, `termMonths`, `status` |
| Вилка | `fork.rateFrom`, `fork.rateTo`, `fork.zone`, `fork.thresholds{approveMax, rejectMin}`, `fork.calculatedAt` |
| Плашка | текст по `fork.zone` (три готовых текста на фронте): `APPROVE` — решение автоматически; `UNDERWRITER` — посмотрит специалист; `REJECT` — будет отказ |
| Пятна | `id`, `type`, `title`, `clientHint`, `pricePp`, `closeMethod` (может быть `null`), `status`, `addedBy`, `source`, `removable`, `answerOptions` |

**Вилка.** Если `rateFrom == rateTo`, показывается одна ставка («Ставка 18,2%»), полоса не рисуется
(⚠️ от себя). Края вилки плавно двигаются при пересчёте (анимация).

**Состояния пятна:**
- `OPEN` — карточка с кнопкой по `closeMethod`, цена «до −X п.п.»;
- `ON_REVIEW` — «Передано на проверку специалисту», кнопки нет;
- `CLOSED` — галочка, свёрнуто;
- `closeMethod = null` (неустранимый стоп-фактор) — вместо кнопки надпись «Устранить нельзя» ⚠️ от себя;
- стоп-фактор `STOP_FACTOR` — красный `Alert` (сделано).

**Кнопки:**
- «Отправить заявку» — `POST /applications/{id}/submit` (если `SUBMIT` есть в `availableActions`; если открыт устранимый
  стоп-фактор, бэк не блокирует, а решение будет отказом — показываем предупреждение ⚠️ от себя);
- «Отменить заявку» — `POST /applications/{id}/cancel` с подтверждением в `Modal`;
- «Начать заново» — только на моках, в API такой операции нет ⚠️ от себя.


**Статус:** список пятен, закрытие, подача, анимация вилки, одна ставка, красный `Alert` для стоп-фактора — сделано на моках. Диалоги закрытия (2.4а) — не сделаны: сейчас в запрос уходит только способ закрытия.

### 2.4а. Диалоги закрытия пятна (T37)
`POST /applications/{id}/spots/{spotId}/close`; тело зависит от `closeMethod`:

| `closeMethod` | Что видит клиент | Тело запроса |
|---|---|---|
| `CONNECT_SOURCE` | «Подключить <источник>?» Что получим, зачем, кнопка «Разрешить» | `sourceCode` (из `spot.source`), `consent: true` |
| `ANSWER` | кнопки вариантов `answerOptions` и/или текстовое поле; можно приложить документ | `optionCode` и/или `text`, по желанию `documentId` |
| `UPLOAD` | выбор файла, подсказка, какой документ подойдёт; **сумма договора** и **срок, мес.** | `documentId`, `contractAmount` (копейки), `contractTermMonths` |
| `PAY` | реквизиты и сумма долга, кнопка «Погасить» (имитация) | без полей |
| `ADD_COLLATERAL` | выбор: поручительство собственника (`GUARANTEE`), залог (`PLEDGE`), «не готов» (`DECLINED`); комментарий | `collateralType`, `collateralComment` |

Загрузка файла: `POST /applications/{id}/documents`, `multipart/form-data`, поля `file` и `kind` (по OpenAPI) → `documentId`.
После успеха экран берёт новую заявку из ответа: вилка пересчитана, пятно `CLOSED` или `ON_REVIEW`.
Если проверка отклонила ответ (`lastAnswer.verdict = REJECTED`), пятно снова `OPEN`, клиент видит комментарий.

| Действие | открыть карточку |

### 3.2. Карточка заявки
| Блок | Данные |
|---|---|
| Шапка | компания, ИНН, продукт, сумма, срок, `status` |
| Вилка | та же `ForkBar`; режим андеррайтера с отметками офферов (T36) |
| Пятна | открытые и `ON_REVIEW` с `lastAnswer` (текст, документ, `verdict`); закрытые свёрнуты |
| Сводка | `GET /underwriting/applications/{id}/summary`: `items[]` с `text` и `facts[]` (`source`, `label`), `generatedBy` (`LLM` или `TEMPLATE`) |
| История | `GET /applications/{id}/history` (журнал событий) |

| Действие | Запрос |
|---|---|
| «Принимаю» / «Не принимаю» ответ + комментарий (обязателен при отказе) | `POST /applications/{id}/spots/{spotId}/review` {`verdict`, `comment`} |
| Добавить пятно клиенту (дозапрос) | `POST /applications/{id}/spots` {`type`, `title`, `clientHint`, `closeMethod`, `scoringFactor`} |
| Посмотреть варианты | `GET /applications/{id}/offers` |
| Вынести решение | `POST /applications/{id}/decision` |

Форма «Добавить пятно»: **выбор фактора** `scoringFactor` из четырёх (`debt_load`, `revenue_stability`, `purpose`,
`collateral`) или «без влияния на вилку». Стоп-фактор добавить нельзя. Подписи факторов для экрана придумает фронт ⚠️ от себя.

### 3.3. Таблица вариантов
| | |
|---|---|
| Получает | `offers`: `productCode`, `amount`, `termMonths`, `collateralType`, `fork`, `status`, `isRequested`, `isManual` |
| Показывает | таблица проходящих вариантов (`CALCULATED`, `OFFERED`), пометка «вручную» у `isManual`, чекбокс «предложить клиенту» (1–3 шт.) |
| Ручная правка | поля суммы и срока (`manualOffer`), `override = true`, **комментарий обязателен** |

### 3.4. Решение
Форма `POST /applications/{id}/decision`: `type` (`APPROVED` / `ALTERNATIVE` / `REJECTED`), `comment`
(обязателен при `override` и при отказе), `offerIds` (1–3 для иных условий), `reasonSpotId` (при отказе — пятно-причина).
