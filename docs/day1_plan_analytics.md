# План этапа «Аналитика» (день 1, вся команда)

## Цель этапа

На выходе — набор документов в `docs/` (именно в `docs/`, они идут на сдачу), которые: (а) закрывают обязательные артефакты из ТЗ, (б) являются входом для проектирования — по ним бэкендер, фронтендер и ML-щик смогут работать дальше без лишних вопросов.

**Формат документов:** Markdown в `docs/`, диаграммы — в Mermaid прямо внутри md (живут в гите, диффаются, не нужны внешние инструменты).

---

## Блок 0. Кикофф (30–45 мин, все вместе)

- Вместе перечитываем ТЗ и выписываем **чек-лист обязательных требований** в `docs/requirements-checklist.md`: ограничения 01–08, обязательные артефакты сдачи, критерии успеха.
- Договариваемся о **границах MVP** в первом приближении: берём минимальный сквозной путь (этапы 1–3 из ТЗ) + скоринг + вердикт. Всё остальное — кандидаты на «если останется время».
- Назначаем пары на блоки ниже и фасилитатора (Миша — следит за таймингом и сводит документы).

## Блок 1. Исследование предметной области (1,5–2 ч, две пары)

- **Пара А — клиентская сторона:** JTBD предпринимателя, роли из ТЗ (собственник, гендир, бухгалтер...), какие задачи и боли возникают на каждом шаге. Итог: `docs/jtbd.md` + список ролей и их целей.
- **Пара Б — банковская сторона:** как устроен реальный кредитный конвейер МСБ (документы, источники: БКИ, ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес»), какие проверки на каком этапе. Итог: `docs/domain-research.md` + таблица «этап → данные → источник → проверка».

*Синк 20 мин:* пары рассказывают друг другу, фиксируем открытые вопросы.

## Блок 2. Модель процесса и границы MVP (1,5 ч, все вместе)

- Рисуем **BPMN/activity-диаграмму** кредитного процесса: участники, действия, точки принятия решения → `docs/process-model.md`.
- Финализируем **границы MVP** по MoSCoW: что Must, что Won't (и **почему** — это прямо спросят на защите, критерий «Потенциал») → `docs/mvp-scope.md`.
- Сверяемся с ограничениями: всё внутри продукта (никаких email/SMS в сценарии), веб-интерфейс, синтетические данные, моки вместо реальных интеграций.

## Блок 3. Сценарии и статусная модель (2 ч, две пары)

- **Пара А:** варианты использования + **основной сценарий** (от входа в кабинет до вердикта) + альтернативные ветки (дозапрос, иные условия, отказ) → `docs/use-cases.md`. Без вайрфреймов, но со списком экранов под каждый шаг — это вход для фронта.
- **Пара Б:** **диаграмма состояний заявки** (обязательный артефакт сдачи): статусы, переходы, кто/что инициирует переход → `docs/application-states.md`. Черновик статусов: Черновик → Подана → Проверка полноты → Дозапрос → Обогащение → Скоринг → Рассмотрение → Одобрено / Иные условия / Отказ → Выдача (смоделирована).

*Синк 30 мин:* ветки сценариев должны биться со статусами. Это самое важное согласование дня.

## Блок 4. Данные и интеграции (1,5 ч, две пары)

- **Пара А:** ER-модель данных (сущности: клиент, компания, заявка, продукт, документы, вердикт...) → `docs/data-model.md`. Это вход для схемы Postgres завтра.
- **Пара Б:** список **моков внешних источников** (БКИ, ЕГРЮЛ/ЕГРИП, ФНС): что возвращает каждый, в каком формате, как эмулируем → `docs/external-mocks.md`. Плюс **перечень синтетических данных**: 3–5 компаний, покрывающих все ветки вердиктов.

## Блок 5. Скоринг и место LLM (1–1,5 ч, все вместе — ключевое решение)

- Фиксируем вашу архитектуру: **детерминированная балльная модель как ядро** (факторы из ТЗ: финпоказатели, долговая нагрузка, кредитная история, параметры заявки → веса → оценка риска) → `docs/scoring-model.md`.
- Размечаем, где LLM с открытыми весами создаёт ценность, а где не нужна. Кандидаты: разбор свободного текста цели кредита, генерация человекочитаемого пояснения вердикта, помощь клиенту при заполнении. **Не кандидат:** сам вердикт.
- Отдельно фиксируем риск: какая модель, сколько весит, влезает ли в docker на обычном ПК. Решение-запас: LLM как опциональный сервис, ядро без неё.

## Блок 6. Закрытие этапа (45 мин, все)

- Проходим по чек-листу из блока 0: какие артефакты сдачи уже закрыты, какие остались на следующие этапы.
- Ретро: 10 мин, что заложить в AGENTS.md по итогам дня.
- Миша сводит всё в `docs/`, коммитит, на доске появляются задачи этапа проектирования.

## Критерий выхода из этапа (DoD)

- [ ] Все документы в `docs/` в репо, читаемы человеком не из команды
- [ ] Основной сценарий и диаграмма состояний согласованы между собой
- [ ] Границы MVP зафиксированы письменно с обоснованием
- [ ] У бэкендера есть ER + статусная машина, у фронта — сценарии и список экранов, у ML — модель скоринга с факторами
- [ ] Принято решение по LLM (да/нет/где)

**Типичные ловушки дня:** уйти в бесконечное исследование предметки (таймбоксы жёсткие — ТЗ прямо говорит «не пытайтесь воспроизвести весь банковский процесс») и несогласованность сценариев со статусами (поэтому синк в блоке 3 обязателен).
