# Канбан 2: ML-трек всей командой

Вторая доска — только ML: скоринг, LLM, детерминизм, качество, тесты, сдача.
Теперь ML делают все: бэкенд, фронт и аналитик тоже. Задачи `M01`–`M33`,
заливаются тем же скриптом: `python3 scripts/create_issues.py --file docs/kanban2.md`.

## Почему сейчас «одобряет по настроению»

Скоринг-движок в `ml/` детерминированный: один вход — один ответ (тесты это
проверяют). Недетерминизм приходит из того, как вокруг него устроен процесс:

1. **LLM в пути решения, но без страховки.** Разбор цели (`/purpose`) влияет на
   фактор `purpose` (±0,5 п.п.). Бэкенд зовёт его с общим таймаутом **4 секунды и
   тремя повторами** (`application.yml`, `IoRetry`), а модель на CPU отвечает за
   14–74 секунды. Одна и та же цель то проходит (модель прогрета), то падает по
   таймауту и превращается в «Не удалось понять цель» (`AnswerCloser.closePurpose`).
2. **Вердикт LLM нигде не запоминается.** Каждый повторный ответ клиента — новый
   вызов модели. Модель 4B иногда сама себе противоречит (в обосновании «слишком
   общее», в ответе MISMATCH).
3. **Дата расчёта «плывёт».** Бэкенд передаёт `asOf = сегодня` (`LocalDate.now(clock)`
   в `ForkCalculationServiceImpl`). Возраст бизнеса и срок директора считаются от
   неё, поэтому вилка и стоп-факторы одной и той же заявки меняются со временем и при
   перемотке демо-часов. Однодневка после 15.12.2026 перестанет быть «новым директором».
4. **Правило решения было записано в нескольких местах по-разному.** После M10 и M22
   его исполняет только `AutoDecisionRule` в бэкенде по `docs/decision-table.json`;
   ML вычисляет вилку, но не выбирает итоговый статус заявки.
5. **Правила откалиброваны на пяти персонажах.** У ступенчатых правил есть обрывы
   (рейтинг 699 → 700 даёт −1 п.п., нагрузка 5,0 % → 5,1 % даёт +1 п.п.), а за
   пределами персонажей поведение никто не проверял.
6. **Ответ на аномалию система проверяет только для варианта «ремонт»**, и это
   правило зашито в Java (`AnswerCloser.singleDropRecovered`), а не в правилах `ml/`.

## Правила игры ML

1. **Сначала правила.** Всё, что можно записать условием, живёт в
   `ml/scoring_rules.yaml` под `rules_version`.
2. **LLM — там, где правил было бы слишком много:** свободный текст клиента (цель
   кредита, объяснение аномалии), где пришлось бы писать сотни `if/else` по
   формулировкам. Только модель с открытыми весами, локально.
3. **У LLM есть правила ответов.** Фиксированный набор ответов (enum), сначала
   обоснование, затем цитата-доказательство из входа, затем ответ. Валидатор
   проверяет ответ правилами; нарушил — `UNCLEAR`. LLM даёт признак, решение
   принимают правила. Кредитное решение LLM не принимает никогда.
4. **Детерминизм на трёх уровнях:**
   - *декодирование:* `temperature 0`, `top_k 1`, фиксированные `seed` и `num_ctx`;
   - *версии:* модель по digest, версия Ollama, версия промпта, `rules_version`
     пишутся в каждый ответ и в снимок решения;
   - *мемоизация:* вердикт LLM по одному и тому же входу вычисляется один раз и
     дальше только читается. Повторный расчёт никогда не спрашивает модель заново.
5. **Дата расчёта фиксируется на заявке.** Пересчёт через месяц даёт тот же результат.
6. **«LLM недоступна» ≠ «непонятно».** Если модель не ответила, ответ клиента уходит
   андеррайтеру; отказывать клиенту из-за таймаута нельзя.
7. **Каждое решение воспроизводимо:** снимок входа и версий; пересчёт по снимку
   даёт байт-в-байт тот же ответ, и это проверяется кнопкой и тестом.

**DoD для ML-задач** (в дополнение к общему из `AGENTS.md`): два прогона подряд и
прогон после перезапуска сервисов дают одинаковый результат; тесты зелёные; контракт
(`docs/openapi-ml.yaml`, `docs/openapi.yaml`) и документы обновлены в том же PR.
Код в `ml/` пишут все, ревьюит Лид.
