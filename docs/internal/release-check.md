# План финальной проверки и подготовки к сдаче

Для аналитика: как проверить целостность решения перед дедлайном и какие документы должны быть в
репозитории по ТЗ (`tz_credits.md`, раздел «Технические требования к решению и формат сдачи»).
Проверка делается чтением и с помощью нейросети; итог — журнал расхождений и закрытый список
документов.

## Как проверять

**Не по слоям, а по сквозному пути и по сущностям.** Противоречия почти всегда живут на стыках:
статус называется в документе одним словом, в API другим, на экране третьим. Если проверять отдельно
бэк и отдельно фронт, каждый слой окажется «правильным», а стык — нет. Поэтому этапы ниже идут так:
запуск → карта ТЗ → словарь сущностей → сквозной путь руками → контракты → ML → enterprise →
нарратив → упаковка. Слои по отдельности проверяются только там, где это контракт (этап 5).

**Правила работы с нейросетью:**

1. Давать ей конкретные файлы, а не «весь репозиторий». Каждый промпт ниже называет, какие.
2. Просить список расхождений таблицей с цитатами и путями файлов (`файл:строка`), без исправлений.
3. Каждое расхождение проверять глазами по цитате: нейросеть путает похожие места и придумывает
   несуществующие строки.
4. Код не править. Расхождение — в журнал (формат в конце), исправляет владелец зоны.

**Источники правды — при споре прав тот, кто выше:**

| Что | Источник правды |
|---|---|
| Статусы и переходы заявки | `day1_backend_application-states.md` |
| Правило решения автопроверки | `decision-table.md` / `decision-table.json` |
| Сущности и поля БД | миграции `server/backend/src/main/resources/db/migration`, затем `day1_backend_data-model.md` |
| Публичный API | `openapi.yaml` (сверяется с живым `/v3/api-docs`) |
| API скоринга и LLM | `openapi-ml.yaml` |
| Правила скоринга | `ml/scoring_rules.yaml`, затем `scoring-model.md` |
| Персонажи и их ожидаемые исходы | `synthetic-data.md` |
| Роль ИИ | `ai-policy.md` |
| Принятые решения | `decisions.md` (Р-01 … Р-18) |

## Этап 1. Заморозка версии и запуск с нуля

**Зачем:** ТЗ требует «единый воспроизводимый способ запуска на обычном ПК». Жюри будет запускать
по README, а не по нашей памяти.

1. Договориться с командой о заморозке `main`: дальше только исправления из журнала.
2. На **чистой машине или в чистой папке** сделать `git clone`, пройти инструкцию из README буквально,
   ничего не подсказывая себе. Каждое место, где пришлось догадываться, — в журнал.
3. Проверить: все контейнеры `healthy` (`docker compose ps`), сайт открывается, Swagger открывается
   (`http://localhost:8080/swagger-ui.html`), стартовый экран показывает персонажей.
4. Проверить, что без LLM всё работает (режим по умолчанию), и что режим с LLM описан и включается
   (`docs/demo-ml.md`, `scripts/demo-ml-prepare`).

**Результат:** время от клона до работающего сайта и список шагов, которых не хватает в README.

## Этап 2. Карта ТЗ → решение

**Вход:** PDF ТЗ, `tz_credits.md`, `requirements-checklist.md`.

1. Сверить `tz_credits.md` с PDF: все пункты постановки, технических требований, рекомендаций,
   критериев успеха и ограничений перенесены без потерь.
2. По `requirements-checklist.md`: для каждой строки открыть указанный файл или пройти указанную
   проверку. Ссылки на несуществующие файлы, старые задачи (`T…`) без результата, проверки
   «на словах» — в журнал.
3. Добавить в чек-лист то, что появилось после его написания: ML-трек (M01–M34), воспроизводимость,
   сверку цели с деятельностью, режимы демо ML.

**Промпт:** «Вот текст ТЗ и `requirements-checklist.md`. Составь таблицу: пункт ТЗ — есть ли строка в
чек-листе — какой файл/проверка указаны. Отдельно перечисли пункты ТЗ, которых в чек-листе нет».

**Результат:** чек-лист, где у каждого пункта ТЗ есть живая ссылка или явная пометка «не делаем, потому что».

## Этап 3. Словарь сущностей — одинаковые названия везде

**Зачем:** самая частая и самая заметная жюри ошибка — одна сущность называется по-разному.

Составить таблицу «код — русское название — где встречается» для:

- статусов заявки (12: `DRAFT` … `CANCELLED`) и переходов 1–17;
- типов и статусов пятен, способов закрытия, источников данных;
- продуктов, статусов оффера, типов решения, ролей;
- кодов ошибок API;
- вердиктов LLM (`MATCH`/`MISMATCH`/`UNCLEAR`/`UNAVAILABLE`, `profile`, коды причин аномалий).

И сверить по каждому: документы (`day1_backend_*`, `api.md`, `screens.md`, `use-cases.md`,
`test-scenarios.md`) ↔ `openapi.yaml` ↔ код (enum'ы в `server/backend/src/main/java/.../enums`,
`ml/scoring/schemas.py`) ↔ подписи на экране (`client/frontend/src/types.ts`, `verdictLabels.ts`,
`pages/*`).

**Промпт (по одной группе за раз):** «Вот `day1_backend_application-states.md`, `openapi.yaml`
(схема ApplicationStatus) и `client/frontend/src/types.ts`. Выпиши все статусы заявки в каждом файле
и русские названия. Покажи таблицей, где набор или название расходятся».

**Результат:** словарь (можно оставить в `docs/glossary.md`, жюри это полезно) и список расхождений.

## Этап 4. Сквозной путь руками

**Вход:** `test-scenarios.md` (TS-01 … TS-08, негативные, ML-сценарии), `synthetic-data.md`.

1. Сброс демо (`scripts/reset-demo` — **стирает заявки**, только на своём стенде).
2. Пройти каждый TS **в интерфейсе**, за клиента и за андеррайтера. На каждом шаге сверить:
   статус, вилку ставки, пятна, тексты кнопок и подсказок — с ожидаемым в сценарии и в
   `synthetic-data.md`.
3. Отдельно — то, что требует ТЗ (постановка задачи п.5 и критерии 01, 04):
   - данные сохраняются: перезагрузить страницу, выйти и зайти — заявка на месте;
   - состояние меняется последовательно: недопустимое действие не появляется на экране;
   - пользователь без банковской экспертизы понимает, что происходит и что делать дальше
     (критерий 03): нет кодов вроде `EQUIPMENT`, `promptVersion`, английских статусов.
4. Негативные проверки из раздела 3 сценариев и выключенная LLM (режим `off`).

**Результат:** по каждому TS — «прошёл / не прошёл на шаге N, что увидел, что ожидалось», со скриншотом.

## Этап 5. Контракты и документация API

1. `openapi.yaml` ↔ живой `/v3/api-docs` (Swagger): все эндпоинты, поля, обязательность, коды ответов.
   **Промпт:** «Сравни эти две спецификации OpenAPI: эндпоинты, которых нет в одной из них, и поля
   схем, которые отличаются именем, типом или обязательностью».
2. `api.md` ↔ `openapi.yaml`: человеческое описание не противоречит контракту.
3. Postman-коллекция: прогнать `scripts/check-determinism` (newman, два прогона) — все проверки
   зелёные, расхождений нет. Каждый эндпоинт из `openapi.yaml` есть в коллекции.
4. `openapi-ml.yaml` ↔ `api.md` (таймауты ML) и `openapi-mocks.yaml` ↔ `day1_backend_external-mocks.md`.
5. Автотесты: бэкенд `mvn test` (с Docker — включая golden-master), ML — команда из `ml/README.md`.
   Записать числа «прошло / всего».

## Этап 6. Модель кредитного решения и ИИ

1. `scoring-model.md` ↔ `ml/scoring_rules.yaml`: базовые ставки, пороги, вклады, цены пятен.
2. `decision-table.md` ↔ `day1_backend_application-states.md` (переходы 6–9) ↔ `scoring-model.md` (§5).
3. Исходы персонажей в `synthetic-data.md` ↔ `test-scenarios.md` ↔ эталон
   `server/backend/src/test/resources/golden/persona-paths.json`.
4. `ai-policy.md`: каждое утверждение («LLM никогда не…», «без LLM…») проверяемо и совпадает с
   поведением на этапе 4.
5. `ml-quality.md`: цифры воспроизводятся командой из отчёта; цель ≥ 90 % по цели кредита **не
   достигнута (87,2 %)** — это должно быть сказано честно в документе и в питче.

## Этап 7. Enterprise-критерии и ограничения ТЗ

Пройти по критерию успеха 05 и ограничениям 01–08:

- безопасность: роли и доступ (клиент видит только свою компанию), упрощение `X-Demo-User` вместо
  логина явно описано как демо-упрощение; секретов нет в репозитории (`git grep` по `password`,
  `token`, `key`), всё в `.env`, есть `.env.example`;
- надёжность: что происходит при недоступности моков и ML (таймауты, повторы, circuit breaker,
  «передано специалисту»), идемпотентность и журнал аудита;
- сопровождение: миграции БД, версии правил и моделей, воспроизводимость (`verify`);
- независимость от платного: `THIRD_PARTY_NOTICES.md` — у каждой зависимости версия и открытая лицензия;
- автономность: все внешние источники — моки, список смоделированных интеграций;
- версии зафиксированы: lock-файлы во всех модулях (`pom.xml` с версиями, `requirements.txt`,
  `package-lock.json` фронта), версии образов в `docker-compose.yml`.

## Этап 8. Продуктовая часть и нарратив

Рекомендации ТЗ 01–05 и критерий 06 «потенциал развития»:

- `concept.md`, `jtbd.md`, `day1_backend_domain-research.md` — исследование и потребности;
- `mvp-scope.md` — границы MVP, MoSCoW с обоснованием, что не вошло и почему;
- `decisions.md` — каждое решение с причиной; проверить, что решения не противоречат друг другу и коду;
- связь «потребность → сценарий → экран/функция»: каждая функция из `screens.md` объяснена
  потребностью, каждая потребность из `jtbd.md` закрыта функцией или явно отложена;
- ограничения и развитие: что дальше (калибровка `calibration.md`, LLM, интеграции).

## Этап 9. Финальная упаковка

1. Все записи журнала с критичностью «блокер» закрыты.
2. README — финальная версия (см. ниже), ссылки рабочие.
3. Тег версии (например `v1.0-submission`) и commit hash — в README и в форме сдачи; после дедлайна
   коммиты не учитываются.
4. Если репозиторий приватный — доступ аккаунту жюри `alfa-hack-2026`.
5. Публичный стенд (желательно): ссылка в README, сценарий проверки на нём проходит.
6. Финальный прогон этапа 1 с нового клона по тегу.

## Журнал расхождений — формат

| id | Этап | Файл:строка или экран | Что сказано / что видно | Как должно быть (источник правды) | Критичность | Кому | Статус |
|---|---|---|---|---|---|---|---|

Критичность: **блокер** — жюри не запустит или не пройдёт сценарий; **важно** — противоречие в
документах или на экране, заметное при проверке; **косметика** — формулировки, опечатки.
