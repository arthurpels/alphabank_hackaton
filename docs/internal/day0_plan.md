## Этап 0. Подготовка (день 0, до старта разработки)

- Монорепо: `backend/`, `frontend/`, `ml/`, `docs/`, `docker-compose.yml` в корне.
- **AGENTS.md** в корне: правила для нейронки (без коммитов, без соавторства, рабочие заметки в `.docs/`, сдаваемая документация в `docs/`, стиль кода, что нельзя трогать чужие модули без таски на доске).
- Канбан: колонки типа Backlog → In Progress → Done (раз без ревью, то Definition of Done = «запускается + не ломает чужое»).
- Скелет docker-compose: postgres + пустые сервисы backend/frontend. Проверить, что `docker compose up` поднимается у всех.

## Этап 1. Аналитика (день 1, всей командой)

Это самый важный день, на нём не экономить. Артефакты (сразу в `docs/`):

- **Границы MVP**: какие этапы из «минимального сквозного пути» берём, что явно выкидываем и почему (это потом спросят на защите — критерий «Потенциал»).
- **Варианты использования + основной сценарий** (без вайрфреймов, как решили).
- **Диаграмма состояний заявки** — она же обязательный артефакт сдачи. Статусы типа: Черновик → Подана → Проверка полноты → Дозапрос → Обогащение → Скоринг → Решение → (Одобрено / Одобрено на иных условиях / Отказ) → Выдача (смоделирована).
- **Модель процесса** (BPMN или activity-диаграмма) и **ER-модель данных**.
- **Список моков внешних источников**: БКИ, ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес» ФНС — что эмулируем и в каком виде (ограничение 04).
- **Разметка скоринга**: как вы и решили — детерминированная балльная модель как ядро (формализованные правила, которые можно объяснить жюри), LLM — только там, где детерминизм невозможен (например, разбор свободного текста цели кредита или генерация пояснения вердикта), с фиксированными промптами и аргументами. Это решение зафиксировать текстом — оно прямо бьётся с разделом «Скоринг и логика кредитного решения» в ТЗ.

## Этап 2. Проектирование (конец дня 1 — день 2)

- **API-контракт первым**: OpenAPI-спека до кода. Это критично — фронт сразу работает с моком по контракту и не ждёт бэк.
- Схема БД (миграции, Postgres), статусная машина заявки как явный компонент бэка.
- Распределение: кто какие сервисы/экраны пилит, зависимости между задачами на доске.

## Этап 3. Параллельная разработка (дни 2–5)

- **Backend (Spring Boot)**: сначала mock-ответы по OpenAPI для фронта → потом реальная логика: CRUD заявки, статусная машина, моки внешних источников, скоринг-сервис.
- **Frontend**: экраны по сценарию, работа на моках с первого дня.
- **ML**: балльная модель скоринга (конфигурируемые правила/веса), при необходимости локальная LLM с открытыми весами как отдельный сервис в compose.
- **Синтетические данные** — отдельная задача с первого дня разработки: 3–5 клиентов/компаний, покрывающих все ветки вердиктов (одобрение / иные условия / дозапрос / отказ). Без этого e2e-сценарий не собрать.
- Ежедневные 15-мин созвоны, кросс-модульные просьбы — через доску.

## Этап 4. Интеграция и пакет сдачи (дни 5–6)

- Сквозной e2e: заявка → все статусы → вердикт, на синтетических данных.
- Чек-лист обязательных артефактов (это прямо чек-лист из ТЗ): README с инструкцией запуска, архитектурная схема, OpenAPI/Swagger, коллекция запросов, диаграмма состояний, модель данных, тестовые сценарии, THIRD_PARTY_NOTICES, тестовые учётки.
- `docker compose up` с нуля на чистой машине — обязательная проверка.

## Этап 5. Финал (день 6–7)

- Деплой на бесплатный хостинг (жюри хочет живой прототип, не скриншоты).
- Репетиция демо по основному сценарию.
- **Тег/хеш — минимум за полдня до дедлайна**, дальше только в отдельной ветке.

---

**Главные риски, которые я бы назвал команде сразу:**

- **LLM в докере** — самая тяжёлая часть. Заранее решить: какая модель, сколько весит, влезает ли в «обычный ПК». Если нет — честно зафиксировать LLM как опциональный компонент, а ядро сделать полностью детерминированным (ТЗ это прямо разрешает: «ИИ приветствуется, но не обязателен»).
- **API-контракт должен появиться в день 2**, иначе фронт и бэк разойдутся и интеграция съест последние два дня.
- **Синтетические данные нельзя оставлять на конец** — от них зависит демо.
