# Реестр решений

Ключевые продуктовые и технические решения прототипа: что решили, почему и
где это отражено.

| # | Вопрос | Решение | Почему | Где отражено |
|---|---|---|---|---|
| Р-01 | Используем ли репутационные данные (отзывы, соцсети, новости)? | Нет, это направление развития; мок не заводим | слабый сигнал, который не может сам привести к отказу; ценность подхода «данные вместо залога» закрывают ОФД, маркетплейс и эквайринг | `day1_backend_domain-research.md`, `mvp-scope.md` |
| Р-02 | Как ведём себя, если внешний источник недоступен или не нашёл данных? | Отдельного пятна «источник недоступен» нет. Ответ `404` — сообщение клиенту, пятно остаётся открытым; таймауты и ошибки `500` обрабатывает бэкенд | клиент понимает, что произошло, и может закрыть пятно другим способом; сбой источника не ломает заявку | `day1_backend_external-mocks.md`, T23 |
| Р-03 | Где хранятся данные демо-персонажей? | Только в `synthetic-data.md`; моки и seed берут данные оттуда. ИНН персонажей проходят проверку контрольной суммы | один источник правды вместо нескольких расходящихся копий; валидные ИНН нужны, чтобы проверка ИНН не отклоняла персонажей | `synthetic-data.md`, `day1_backend_external-mocks.md` |
| Р-04 | Где хранится согласие клиента на подключение источника? | В БД (`application_source`); мок только проверяет, что согласие передано | согласие — юридически значимый факт, его нужно хранить вместе с заявкой и видеть в журнале | `day1_backend_data-model.md` |
| Р-05 | Нужны ли лимиты полномочий андеррайтера? | Нет. Ручная правка условий — только с обязательным комментарием, разница условий пишется в журнал | распределение заявок и полномочия — зона внутренней системы банка; кабинет андеррайтера её эмулирует | `mvp-scope.md` («Упрощения»), `day1_backend_process-model.md` |
| Р-06 | Блокируем ли подачу заявки с непогашенным устранимым стоп-фактором? | Нет. Заявка уходит на автопроверку и получает отказ с причиной — этим стоп-фактором | клиент сам решает, когда подавать; отказ всегда объяснён | `day1_backend_application-states.md` (переход 8) |
| Р-07 | Как обеспечивается воспроизводимость решения? | Версия правил (`rules_version`) задаётся в файле правил скоринга, возвращается в каждом ответе скоринга и сохраняется в снимке вилки и в решении | любую вилку и решение можно пересчитать по той же версии правил и получить тот же результат | `scoring-model.md`, `day1_backend_data-model.md` |
| Р-08 | Чем заканчивается путь ИП Петрова (строителя)? | Иными условиями от андеррайтера: 1 950 000 ₽ на 36 месяцев без обеспечения | иначе ветка «иные условия от андеррайтера» не покрыта ни одним персонажем; одобрение уже показывают Кофейня и Техснаб | `synthetic-data.md`, `day1_backend_application-states.md` |
| Р-09 | Может ли клиент отменить заявку во время дозапроса? | Да | клиент может передумать в любой момент, пока решение не принято | `day1_backend_application-states.md` (переход 16) |
| Р-10 | Текущая просрочка в БКИ — устранимый стоп-фактор? | Нет, неустранимый: автоотказ | погашение просрочки в другом банке нельзя подтвердить в рамках продукта | `day1_backend_domain-research.md`, `day1_backend_external-mocks.md` |
| Р-11 | Что происходит при неустранимом стоп-факторе? | Автоотказ в автопроверке; вилка и остальные пятна не считаются | собирать данные бессмысленно: решение не изменится | `day1_backend_external-mocks.md`, `day1_backend_data-model.md` |
| Р-12 | Где источник правды по параметрам продуктов (суммы, сроки)? | Справочник продуктов в БД; правила скоринга используют те же значения | параметры продукта видит клиент при подаче, и скоринг должен считать по ним же | `scoring-model.md`, `synthetic-data.md` |
| Р-13 | Кто проверяет ответ клиента на аномалию выручки? | Система, если данные подтверждают причину: правила `answer_checks` в `ml/` — «ремонт» (падение разовое, в следующем месяце выручка восстановилась), «сезонность» (такое же изменение год назад); иначе, и для причин без проверки данными, — андеррайтер. Свободный ответ сначала разбирает словарь причин, затем LLM с правилами ответов | андеррайтер видит только то, что система не может проверить сама; проверку данными делают правила, а не LLM | `day1_backend_process-model.md`, `ai-policy.md`, `ml/scoring_rules.yaml` (`answer_checks`), M14, M16 |
| Р-14 | Кто проверяет описание цели кредита? | Система: словарь допустимых целей для продукта; локальная LLM — только если словарь не справился и LLM включена. Ответ LLM проверяет валидатор правилами ответов (цитата из текста клиента, без сомнений в обосновании), иначе «непонятно — напишите подробнее». Вердикт хранится в ответе клиента и повторно для того же текста не запрашивается; LLM недоступна — ответ уходит специалисту | решение остаётся детерминированным и воспроизводимым, LLM не обязательна для работы, отказа из-за недоступности модели нет | `ai-policy.md`, `day1_backend_process-model.md`, `THIRD_PARTY_NOTICES.md`, M05, M11 |
| Р-15 | Где используется LLM? | Только для разбора свободного текста клиента — цели кредита и объяснения изменения выручки — там, где правил по формулировкам было бы слишком много; и опционально для сводки андеррайтеру. LLM даёт признак, решение принимают правила. Модель с открытыми весами (`qwen3:4b`), локально, выключена по умолчанию; детерминизм — жадное декодирование, модель по digest, версия промпта, мемоизация вердиктов | ИИ применяется там, где создаёт понятную ценность, а кредитное решение остаётся воспроизводимым | `ai-policy.md`, `mvp-scope.md`, `THIRD_PARTY_NOTICES.md`, M01, M02, M07 |
| Р-16 | Нужно ли показывать на демо новостную ленту под клиента? (фраза из технических требований ТЗ) | Нет | организаторы хакатона подтвердили, что пункт про новостную ленту не относится к данному кейсу | `requirements-checklist.md` (Т-11) |
| Р-17 | Заявка в зоне отказа (левый край ≥ порога отказа): сразу отказ или сначала сетка иных условий? | Сначала сетка: есть проходящий вариант — `COUNTER_OFFER`, нет — `REJECTED` с самым дорогим незакрытым пятном | вариант сетки проходит по тем же правилам, что и автоодобрение; прогон движка: у 178 из 23 748 заявок в зоне отказа такой вариант есть (дольше срок с поручительством или овердрафт). На персонажей не влияет | `decision-table.md`, `day1_backend_application-states.md` (переходы 7–8), `scoring-model.md` |
| Р-18 | Проверяем ли, что цель кредита соответствует деятельности компании? | Да, после проверки цели против продукта: LLM с правилами ответов сверяет цель с основным ОКВЭД из ЕГРЮЛ. «Не похоже» — не отказ, а ответ специалисту с причиной; траты, нужные любому бизнесу, подходят всегда; без LLM сверка не выполняется | иначе производитель компьютеров с целью «кофемашина» получает скидку за «понятную цель»; автоматический отказ дал бы ложные отказы (кофемашина для офиса), поэтому решает человек | `ai-policy.md`, `ml/llm.yaml` (`profile`), `ml/okved.yaml`, M33 |
| Р-19 | Учитываем ли действующие кредиты клиента при расчёте долговой нагрузки? | Да. В нагрузку входят платёж по новому кредиту, точные платежи по договорам нашего банка (другие заявки компании в статусах «Оформление» и «Выдано») и открытые кредиты из БКИ с ненулевым остатком. Платёж по кредитам из БКИ оценивается условно: аннуитет на остаток за 36 мес. по расчётной ставке (кредит с графиком) или 5 % остатка в месяц (карта, овердрафт). У овердрафта метрика «лимит / выручка», действующие платежи в неё не входят | ТЗ называет «существующие обязательства» фактором скоринга; без этого клиент после выдачи мог бы подать вторую заявку с прежней вилкой. В БКИ-моке есть лимит и остаток, но нет платежа и срока, поэтому оценка — допущение прототипа: параметры лежат в `ml/scoring_rules.yaml` (`existing_obligations`) и версионируются через `rules_version` | `scoring-model.md`, `day1_backend_external-mocks.md`, `mvp-scope.md`, `test-scenarios.md` (TS-08) |
